# office-hours Instructions

## コンテキスト読み込み

相談内容に応じて以下を読む:

1. `docs/DESIGN.md` — アーキテクチャ、技術選定の根拠
2. `docs/ROADMAP.md` — 計画とフェーズ
3. 関連するソースコード

## よくある相談トピック

### 1. 音声入力アーキテクチャ

**WhisperKit 関連:**
- モデル選択 (tiny/base/small) とパフォーマンスのトレードオフ
- リアルタイム音声認識 vs バッチ処理
- 言語検出と多言語対応
- 音声活動検出 (VAD) の実装

**llama.cpp 関連:**
- テキスト補正・変換のプロンプト設計
- モデルサイズとデバイス性能の制約
- 推論速度の最適化
- カスタム辞書の組み込み方法

### 2. ローカル処理・プライバシー

- すべての処理をデバイス上で完結させる設計
- モデルのバンドル vs ダウンロード
- データの保存範囲と削除ポリシー
- App Tracking Transparency への対応 (不要の場合の根拠)

### 3. macOS / iOS デュアルプラットフォーム

- CalameKit (SPM) での共通ロジックと分岐点
- macOS: メニューバーアプリのライフサイクル
- iOS: Keyboard Extension の制約 (メモリ 60MB, ネットワーク制限)
- プラットフォーム固有 UI の設計パターン
- `#if os(macOS)` の使いどころ

### 4. TCA 設計パターン

- Feature の分割粒度
- 親子 Reducer の結合方法
- Navigation の設計 (Stack vs Tree)
- 長時間実行 Effect (音声認識) の管理
- DependencyKey の粒度

### 5. SwiftData 設計

- モデル設計のベストプラクティス
- 大量の入力ログのパフォーマンス
- マイグレーション戦略
- Keyboard Extension からのデータアクセス (App Group)

### 6. Keyboard Extension 固有

- メモリ制限 (60MB) 内でのモデルロード
- Full Access 権限の要否
- ホストアプリとの連携 (App Group)
- UI カスタマイズの制約

## 回答のスタイル

- **トレードオフを明示**: 「Aの方が良い」ではなく「Aは{メリット}だが{デメリット}、Bは...」
- **根拠を示す**: Apple のドキュメント、TCA のガイドライン、実際のコードを参照
- **具体例を出す**: 抽象的な説明だけでなく、コードスニペットも提示
- **DESIGN.md との整合性**: 既存の設計方針との整合性を確認
