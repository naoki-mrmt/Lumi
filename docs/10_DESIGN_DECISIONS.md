## ADR-001: 9人制特化、6人制対応はしない

**日付**: 2026-05-02

**背景**: バレーボール統計アプリは6人制が主流。9人制対応は限定的。

**判断**: 9人制特化、6人制対応はスコープ外

**理由**:
- 9人制は6人制のサブセットではない（ルール独自・ローテなし）
- 「両対応」を狙うと両方とも中途半端になる
- 9人制ニッチ市場で「最高のもの」を作る方が価値が高い

**影響**:
- データモデルがフリーポジション前提
- ローテ別分析を実装しない
- 6人制ユーザーは諦める

## ADR-002: TCAアーキテクチャの採用

**日付**: 2026-05-02

**背景**: SwiftUIアプリの状態管理選定

**判断**: TCA（The Composable Architecture）を採用

**理由**:
- 状態管理が宣言的、複雑な試合進行ロジックを記述しやすい
- 副作用が型レベルで管理され、テストが書きやすい
- TCA TestStore で状態遷移テストが綺麗
- 個人開発でも長期メンテに耐える構造化を強制

**影響**:
- ボイラープレート増加を許容
- 学習コスト発生（既習得済みなので問題なし）
- 開発者は本リポでの実装を学ぶ必要

## ADR-003: Supabase採用（vs Firebase）

**日付**: 2026-05-02

**背景**: バックエンドBaaS選定

**判断**: Supabaseを採用

**理由**:
- PostgreSQLベース → SQLで柔軟集計可能（Phase 2の対戦相手DB等で活きる）
- Supabase Swift SDK は公式・成熟（v2.0+、4年開発）
- Free tier が個人開発に十分
- Row Level Security でマルチテナント対応がきれい
- Firebaseロックインを避けられる

**影響**:
- Postgres前提のスキーマ設計
- Sentry等の付帯サービスはFirebase外で構築

**代替案**: Firebase（Firestore + Auth + Crashlytics）。Swift SDKの歴史は長いがSupabaseも成熟。Postgres非対応がデメリット。

## ADR-004: SwiftData採用（vs Core Data）

**日付**: 2026-05-02

**判断**: SwiftDataを採用

**理由**:
- iOS 17+から利用可能、最低OS（26）でフル機能利用可
- SwiftUIとの相性が良い、ボイラープレート少ない
- Core DataのSwift wrapperとして将来性が高い

## ADR-005: 入力UIは「3モード」設計（クイック/スタンダード/詳細）

**日付**: 2026-05-02

**背景**: 「全部記録したい」と「入力負荷を下げたい」の両立

**判断**: クイック・スタンダード・詳細の3モード切替

**理由**:
- ママさん層（簡易）と実業団（詳細）で要件が違う
- 同じデータモデルで詳細項目はnull可とすれば実装は1系統
- 試合の重要度や入力者のスキルで使い分け可能

**影響**:
- データモデルにoptionalな詳細項目を持たせる
- UI設計を3バリエーション分作る

## ADR-007: ロール分離（Recorder 1台 / Viewer複数台）

**日付**: 2026-05-02

**判断**: 入力1端末・閲覧複数端末

**理由**:
- 同時複数入力はデータ整合性問題を招く
- 入力者が1人いれば運用上問題ない
- Viewerは試合コードでパスワードレス参加（UX最優先）

## ADR-008: Recorderはアカウント必須、Viewerは試合コードのみ

**日付**: 2026-05-02

**判断**: 認証コストを Recorderに集中、Viewerはゼロコスト

**理由**:
- Recorder = データ所有者、本人特定が必要（復旧・所有権のため）
- Viewer = ベンチ即入りたい、認証コストはUX最悪
- 試合コード自体が試合限定の入場券として機能（24時間有効）

## ADR-009: クラウドが正本、ローカルはバッファ

**日付**: 2026-05-02

**判断**: Source of Truthはクラウド、ローカルは送信失敗時の保留

**理由**:
- データの真実の源を一意に保つ
- 端末紛失・故障に強い
- マルチデバイス整合性が自然に取れる

**懸念と緩和**:
- オフライン耐性 → ローカルバッファで完全自律稼働可

## ADR-010: 物理削除（論理削除しない）

**日付**: 2026-05-02

**判断**: シンプルさ重視で物理削除

**理由**:
- 個人開発、データ復元は本来の業務上の課題ではない
- スキーマもクエリもシンプルに保てる
- 監査ログ等のニーズもない

**緩和策（誤削除事故防止）**:
- 削除前に試合名入力で確認（GitHub repo削除と同じ）
- 削除前にローカルJSONバックアップ自動生成

## ADR-011: 3点連続交代ローカルルール非対応

**日付**: 2026-05-02

**判断**: 標準JVAルールのみ対応、地域ローカルルールは非対応

## ADR-014: フォーメーションはセット開始時宣言・タイムアウト時変更可

**日付**: 2026-05-02

**判断**: B+案（セット開始時に1つ宣言、TO時のみ変更記録）

**理由**:
- 1セット中にガラッと変える運用は稀（基本固定）
- セット間/TO時の作戦変更はよくある
- ラリーごと記録は入力負荷が高すぎる

## ADR-015: 相手チームは背番号のみ運用、サービス順管理しない

**日付**: 2026-05-02

- 入力負荷を最小化

## ADR-017: アタック決定/打数の定義はData Volley準拠

**日付**: 2026-05-02

**判断**: Data Volley標準定義を採用

**理由**:
- 実業団層が慣れている定義
- データバレーからの移行を意識
- 業界標準に揃える

**定義**:
- 打数 = アタック試行回数全て（被ブロック含む）
- 決定数 = 相手コートにダイレクトに得点（ブロックアウト含む）
- 失点 = 被ブロック + アウト/ネット/タッチネット等のミス

## ADR-026: 試合コードは6桁・紛らわしい文字を除外・24時間失効

**日付**: 2026-05-02

**判断**: `23456789ABCDEFGHJKLMNPQRSTUVWXYZ` の32文字から6桁

**理由**:
- 6桁で32^6 ≒ 10億通り、衝突は実用上ゼロ
- 0/O・1/I/l を除外して見間違い防止
- 24時間失効でセキュリティ確保

## ADR-027: プロダクト名「Lumi」採用

**日付**: 2026-05-02

**判断**: プロダクト名を「Lumi」（リュミ）に決定

**詳細**:
- 正式名称：**Lumi**
- App Store 副題：**Lumi — Volleyball Scouting**
- Bundle Identifier：`com.muramoto-co.lumi`
- リポジトリ・ルートディレクトリ名：`lumi/`
- Xcode プロジェクト名：`Lumi.xcodeproj`

**由来**: フランス語 lumière（光）の短縮形。「データに光を当て、試合の本質を映し出す」という意図。

**理由（候補比較からの選定）**:
- 4文字で短く、ロゴが映える（Apple系プロダクト命名美学に一致：Vision/Notes/Pages/Mela 等）
- 「光を当てる=分析する」のメタファーが本アプリのデザイン哲学（沈黙のスカウティングツール）と完全に一致
- ダーク背景に細い光のような文字でロゴを配置すると、デザイン哲学との視覚的整合が取れる
- 国際展開時もどの言語でも発音できる
- フランス系の知的・エレガントな響き

**他候補との比較**:
- Volée（バレー語源、しかしアクサン記号のロゴ化やや煩雑）
- Repère（指標・知的、ただしやや硬い）
- Vigie（見張り台・観察、業務ツールっぽさが強い）

**影響**:
- ドキュメント全体のプロダクト名表記を「Lumi」に統一済み
- リポジトリ名・Xcodeプロジェクト名・Bundle Identifier 全部統一
- 副題で「Volleyball Scouting」と明示し、ジャンル検索性を確保
